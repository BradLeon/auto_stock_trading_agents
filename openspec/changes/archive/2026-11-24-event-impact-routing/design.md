# Design

## Context

动机见 proposal.md。与实现相关的现状如下。

- **Chief 的基本面二选一。** 对每个标的，Chief 只读一份基本面：4 天内有效的财报事件评审优先，否则读例行更新（`decision_requirements.fundamental_coverage`）。重大事件评审如果做成 `fundamental-event` 的一种模式，会遮蔽财报评审。
- **信息简报只覆盖 18 个 targets。** `fact_changes` 是不带评级的事实列表，`impact_candidates` 实际为空。`triage.py` 有一个 0–1 的重要性分，但没有落到事实上。
- **层次分析只读链证据。** 链证据是已映射到命题维度的观测。新闻类证人 DOWJONES、SEMIANALYSIS、TRENDFORCE 自 8 月起停产，由前置 change `article-witness-observations` 修复。
- **板块配置的预算换算。** 层的配置结论经 `layer_utilization` 映射为预算使用率。代码已经保证 `weight_cap` 是天花板，风控读静态上限。
- **事件路由只认日历事件。** `event_routes.yaml` 现在只接日历事件（财报、FOMC、宏观数据）；dispatcher 每小时 :05 和 :35 消费事件。
- **配置血缘按内容哈希。** 495c0db 之后，配置血缘按 YAML 解析后的内容哈希。这次在 `ai_hardware.yaml` 新增风险命题会使层评审的血缘变化，这是预期的重算。

## Goals / Non-Goals

**Goals:**
- 一件重大事件当天收盘后的那一轮内，按影响面进入基本面与层次分析，Chief 当晚例行周期可见。
- 公司特有与整层共同两部分各有唯一认领者，Chief 侧按事件簇对齐。
- 评级可被验证：上线前过基准集门槛，上线后每周校准。

**Non-Goals:**
- 不临时启动 Chief，不改交易门槛、风控限额与 `weight_cap`。
- 不做盘中实时新闻流，仍以已入库新闻为输入。
- 不让模型改配置文件，新增命题和风险项只出建议。
- 宏观不进层次分析。

## Decisions

### D1. 成分评级在简报汇总之后单独做一次，每个简报一次请求（2026-11-13 用户选定方案 A）
在简报的事实汇总好之后（`fact_changes` 与 `source_evidence` 已经齐备），对**这个标的当天的全部事实**单独调用一次评级：新模块 `agents/information/event_components.py`、新提示词 `information-event-components`、新路由角色 `event_component_rating`（flash，关闭推理）。模型给出成分的划分（引用事实下标）与各项评级；引用片段由代码按事实下标取自 `source_evidence`，不由模型书写。
- 理由：
  - 抽取缓存的版本号包含 `extract.py` 与 `research-insight` 提示词的全文（`execution_versions` 的 `template_source`）。把成分并进逐篇抽取，哪怕开关关着，只要改了这两个文件，dispatcher 一重启所有近 7 天文章的抽取缓存就会失效、要重抽几百次。单独评级不改这两个文件，开关关闭时与现状完全一致。
  - 一次看到该标的当天的全部事实，归簇与"是否升级"的判断比逐篇判断更准。
- 代价：开关打开后每个简报多 1 次 flash 请求（18 个 target 加轻量简报）。
- 备选：并进逐篇抽取（原 D1）。否决：开发期间与上线时各一次全量缓存失效，且跨文章归簇只能靠事后拼接。
- 开关：`config/workflow/event_impact.yaml` 的 `components.enabled`，默认关闭。该文件暂不进入简报的配置血缘（否则新增文件会让已有简报的血缘失效、卡住 Chief）；上线时随第 9 组一起把它纳入 `information-brief`、`layer-review` 的血缘。

### D2. 新颖度由代码和模型分工
- "首发 / 后续"由代码判定：查事件簇过去 7 天的台账。
- "升级"由模型判定，给出理由：重要性或事实是否升级。
- 理由：
  - 首发判断是查表，交给模型会不稳定；
  - "是否升级"是语义判断，按"配置定范围、模型做判读"的原则交给模型。
- 事件簇键沿用简报现有的 `cluster_key`；为空时用"主实体 + 事件类型 + 关键名词"的规范化串，由模型在成分里给出，代码规范化。

### D2b. 评级口径：重要性 + 方向，不用"严重度"（2026-11-15，基准集首轮评测后用户确认）
首轮评测（用户标注 27 条）相邻档一致率 93%，但用户标为严重的有 6 条被漏判。其中 2 条是正面重大事件（美光覆盖至 2030 年逾 35% 营收的长约、SK 海力士与 14 家客户的 LTA）：原口径照搬 MSCI 争议评级的"伤害性质 × 波及范围"，只看负面，正面重大事件被评低。改为：
- `materiality`（重要性）：对预期或论点的改变有多大，正负都算；四档 `minor` / `moderate` / `major` / `critical`。
- `direction`（方向）：`positive` / `negative` / `mixed` / `unclear`。
- 路由按重要性，正面重大事件同样触发基本面重大事件评审；层预算的"只下调"不变，只有负面的风险或冲击能让层下调。
其余漏判集中在"英伟达这类枢纽公司的公司事件是否传导到整条链"（用户判跨层，模型判本公司）。谁是枢纽会随时间变化，让信息岗评级时判断太难，故不做枢纽判断，改为路由兜底（用户 2026-11-15 确认）：产业链成员的"本公司"重大成分，在触发基本面重大事件评审的同时触发其所在层的层次分析，由层次分析依据当期证据判断有无整层传导（有则补认领并可建议下调，无则记"无整层传导"）。代价是成员公司每次重大公司事件多一次层复盘和板块复盘；首轮候选里重大仅 4/91。基准集因此只考核重要性档位与方向，影响面分歧不再算漏判。

### D3. 重大事件评审是新角色，与财报口径叠加
新增任务 `fundamental-material`，对应角色 `fundamental_material_review`、投影 `FundamentalMaterialReview`。
- `fundamental_coverage` 的二选一规则保持不变。
- 决策档案新增可选类别 `fundamental_material`。
- 备选：`fundamental-event` 增加 `event_kind=material`。否决：会参与二选一而遮蔽财报评审，而且记分卡的字段与重大事件的语义不同，容易误读。

### D4. 公司风险项独立维护，不放进财报基线
基线只在财报前 3 天才建，风险项必须全年都有，所以风险项单独成投影，由基本面维护：
- 上线时为 18 个 targets 初始化；
- 每次建基线时刷新；
- 重大事件评审读取最新一版。
- 备选：放进基线。否决：财报窗口外没有最新基线。

### D5. 风险命题复用链证据引擎，换计数规则
- `kind: risk` 的证据来源有两个：链证据观测（含恢复后的文章证人），以及简报中涉及本层的事件成分。
- 判读同样逐簇进行、带缓存。
- 计数从"独立公司说话人"换成"独立来源"：同一出版方或同一原发的转载算一个，并要求至少 1 个一手或权威来源。
- 经营命题的计数规则不动。

### D6. 层次分析的安全网输入（2026-11-15 起触发也纳入成员的重大公司事件，见 D2b）
层次分析的输入包含本层成员所有"重大"及以上的成分，包括标为"本公司"的；但只有影响面为本层或跨层的成分会**触发**层复盘。
- 理由：影响面判错时，层面传导不至于丢失；同时不会因为每个公司事件都触发层复盘而增加成本。
- 补认领次数进入每周校准报告。

### D7. 只下调的约束放在代码里
- 板块配置把层次分析的下调建议换算为档位时，代码钳制两件事：方向只能向下；临时复盘每次最多下调一档。
- 区分临时复盘和例行复盘的依据是触发来源：例行的 `scheduled` 触发，还是 `material_development` 触发。
- 被截断的建议记入 `downgrade_reasons`。

### D8. 事件路由复用 dispatcher 的事件消费
- `event_routes.yaml` 新增 `material_development`，`scope_resolver` 分两种：
  - `component_entity`：公司成分 → `fundamental-material`；
  - `component_layers`：层面成分 → 每个涉及层的 `layer-review`，再接 `sector-review`。
- 简报发布后，由发布路径把合格的成分写成事件候选，dispatcher 在下一个 :05 或 :35 消费。
- 去重键为"事件簇 + 下游任务 + 范围 + UTC 日期"，升级或新成分会使用新的去重键。
- 台账复用 `trigger_runs` 与事件台账，新增成分编号字段。
- 备选：在简报任务里同步调用下游。否决：会绕过 dispatcher 的租约、重试和台账。

### D9. Chief 的事件对齐视图在代码里完成
- `assemble.py` 按 `component_refs` 把同一事件簇下的投影片段聚到一起，渲染为一个块。
- 主理人 skill 加一条：同一事件簇的多份评估是一件事的不同部分，不要重复计算。
- 备选：让 Chief 自行对齐。否决：容易漏对，也不可审计。

### D10. 评级基准集与校准
- **基准集**：我从库中挑约 60 个候选成分，覆盖黄仁勋事件、出口管制、非财报公告与明显的噪音，用户从中选定 40 个并标注。
- **门槛**：重要性相邻档以内一致 ≥ 85%；用户标为"重大"及以上的成分，模型不得评得更低。
- **周报**：纯代码。超额收益相对层篮子等权计算，窗口为 1–3 个交易日；分歧来自下游复核字段；补认领次数来自层分析投影。

## Risks / Trade-offs

- [评级失准导致过度触发] → 只有"重大"及以上触发；同一簇按日去重；上线前过基准集门槛；每周校准。
- [影响面判错，层面传导丢失] → D6 安全网与补认领计数。
- [基本面和层次分析对同一事件重复计价] → 认领分工写进两边的提示词与规格；Chief 端按事件簇对齐。
- [临时复盘频繁、成本上升] → 按日去重；单次最多下调一档，也降低了反复复盘的必要。用户在 API 侧设额度，应用内不加护栏。
- [新增风险命题导致层评审血缘全部变化，周六需要重算] → 预期之中。上线时间安排在周六例行复盘之前，避免额外一轮。
- [轻量简报增加每日请求] → 只覆盖 9 家产业链成员，且只出成分。
- [新闻证人恢复前风险命题证据不足] → 依赖 `article-witness-observations` 先完成；在它完成之前，风险命题只靠简报成分，独立来源门槛照常执行，不足时判"出现"而不是"承压"。

## Migration Plan

1. 完成 `article-witness-observations`。
2. 按 tasks 分组实施。每组只跑相关测试；新增字段均为 v1 可省略，存量投影不重跑。
3. 评级上线门槛：基准集评测达标后，才打开 `material_development` 路由。在此之前，简报照常输出成分，但不触发任何任务。
4. 回放验收：在隔离环境里回放 2026-11-09 至 11-12 的真实新闻。回放前报请求数。
5. 上线：改定时任务和路由、写生产之前须经用户批准；重启 dispatcher，观察第一次真实触发。
6. 回滚：
   - 关闭路由开关，事件不再触发；
   - 层次分析与板块配置的新字段可以继续保留；
   - 板块配置的"只下调"钳制不影响原有行为，没有下调建议时与现状一致。
