# Design

## Context

- **现状：** TWS 由用户手动启动，依赖 TWS 自带的每日自动重启。本仓只有只读探测脚本 `scripts/probe_phase_f_tws_readonly.py`。
- **可参照实现：** `option_quant_trade_system` 仓库已有 IBC 启动脚本（`start_tws.sh`）和保守守护脚本（`ensure_tws.sh`：端口可达 + API 握手才算成功，冷启动等待 150 秒）。
- **约束：**
  - 实盘账号的 2FA 必须手机确认，无法完全无人值守。
  - 凭据只能放在用户本机的 IBC 配置里。

## Goals / Non-Goals

**Goals：**
- TWS 停在登录界面、进程退出或 API 无响应时，在 10 分钟内自动发起恢复并告警。
- 恢复动作不会误杀正在工作的 TWS。

**Non-Goals：**
- 不绕过 2FA。
- 不切换 paper/live。
- 不改各工作流在 TWS 不可用时的处理逻辑。

## Decisions

### D1. 用 IBC 托管启动

用 IBC 托管 TWS 启动，而不是自写 AppleScript 去点登录界面。IBC 是 IB 生态的事实标准，处理登录、更新对话框和每日重启；自写 UI 自动化脆弱，且要处理凭据输入。

### D2. 守护判据采用“端口可达 + API 握手成功”

只看端口会把“停在登录界面但端口已监听”误判为正常。握手用只读连接，`clientId` 与业务进程区分，探测后立即断开。

### D3. 保守恢复，按顺序升级

1. 端口可达但握手失败：等待最多 60 秒，让 API 完成初始化。
2. 仍失败或端口不可达：经 IBC 重启，最多 2 次，每次等待 150 秒。
3. 仍失败：停止自动动作，发出“需要人工”告警。

全程不在交易时段内主动重启一个握手成功的 TWS。

### D4. 运行方式

launchd 每 5 分钟运行一次守护检查。告警复用现有告警通道（飞书机器人），内容只包含状态和时间，不含任何凭据。

### D5. 2FA 处理

IBC 发起登录后，2FA 推送由用户在手机上确认。守护检查把“等待 2FA”识别为单独状态（端口未监听、IBC 日志显示等待二次验证），告警文案提示用户去确认，而不是反复重启。

## Risks / Trade-offs

- [2FA 超时未确认] → 告警升级为“需要人工”，不再重启，避免锁账户。
- [IBC 与 TWS 版本不匹配] → 安装说明中写明 `TWS_MAJOR_VRSN` 要与已装 TWS 一致；守护检查在 IBC 启动失败时附上 IBC 日志尾部（凭据行脱敏）。
- [守护脚本本身挂掉] → 由 launchd 定时拉起；每日在 clerk-daily 之前写一条心跳。

## Migration Plan

1. 用户安装 IBC 并填写配置。
2. 部署守护脚本并手动执行一次（只探测模式）。
3. 开启 launchd 任务。
4. 观察一次真实的每日重启。

回滚：卸载 launchd 任务即可，TWS 回到手动管理。
