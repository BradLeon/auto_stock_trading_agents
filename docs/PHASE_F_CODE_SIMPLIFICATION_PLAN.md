# 第 1 步：Phase F 切流代码精简改动计划（2026-10-15，计划，未改代码）

## 一、白话结论

- **做法是"加一条简单路径"，而不是"拆掉旧机制"。** 新增"按消费者整体切换"的路由：某个消费者（如 Information）切到新路径后，它所有日常运行都走新路径。现有的精确 scope 机制原样保留、但不再参与日常运行，所以**现有的几百个 Phase F 测试基本不用改**，改动集中、风险可控。
- 新路径上只保留安全底线和真实需要的检查：读取失败显式报错；每天一次数据产品健康检查，失败**自动切回旧路径并告警**（G3）；切换和切回都要有记录。
- 去掉的是：日常运行时的入口证据检查、逐标的×时点的资格查询、持久部署窗口、停止锁存、切换前的兼容性证明和自身产出检查、两层授权。
- 改动后，**改测试或脚本、甚至改业务代码，都不会再让任何"资格"失效**，今天这种反复重做生产补验的循环结束。资格账本和冻结工具保留作审计，不再是前置条件。
- 工作量：约 4 个源码文件修改、2 个新模块、1 个新命令、1 个每日任务、2 个新测试文件。不调用模型，不写生产。

## 三、怎么保证安全底线不受影响

| 安全底线 | 怎么保证 |
|---|---|
| 新路径不能下真单 | 本次只改研究读取边界；券商写禁止与实盘边界 `disabled` 不变，测试覆盖不变 |
| 只有一个实盘入口 | 不碰交易路由；新增"消费者整体行"只允许写在 `projection_read` 边界，写其他边界直接报错（有测试） |
| 审批与记账成对切换 | 联合协调器对这两条边界照旧强制；消费者整体行不能用于它们（有测试） |
| 可回滚 | `rollback` 无前提、随时可做；每日健康检查失败自动执行；全局紧急停止（边界级 disabled）仍然覆盖所有消费者 |
| 读取失败不能被吞成空结果 | 原生读取的失败报错逻辑不变 |
| 留痕 | 每次切换、切回、健康检查都写入只增不改的记录 |

**老实说明放松了什么：** 日常运行不再逐次核对"该标的×时点有没有 7 类原始证据"和"入口证据包是否登记"。替代的是每日数据产品健康检查和失败自动切回旧路径。依据是 TARGET 不要求前者，你已确认以 TARGET 为准。

## 四、测试

新增：

- 路由：精确行优先于消费者整体行；没有任何行时默认旧路径；全局 disabled 仍覆盖消费者整体行。
- 消费者整体新路径：不调用 `assert_enforced`、不查精确资格、不要求部署窗口；精确行的行为与现在逐字一致（直接复用现有测试）。
- 边界限制：消费者整体行写到 `projection_read` 以外的边界被拒绝；审批/记账仍要求联合切换。
- `switch`：健康检查不通过或没有批准记录时拒绝；`rollback` 无条件可用；记录表只增不改。
- 健康检查：文档缺失、无版本/来源、财务血缘缺失、上游简报缺失或过期都判失败；正常数据判通过；不调用消费者读取入口。
- 每日任务：健康检查失败时自动切回旧路径并告警；成功时只写记录。
- 端到端（隔离环境）：Information 切到新路径后，组合级 Information 入口能读文档并发布带血缘的简报；切回旧路径后走旧逻辑。

回归：现有 Phase F 受影响门禁（508 项）与慢速组（114 项）全部重跑；预期现有测试**不需要修改**。如有个别失败，逐条说明原因再改。

## 五、做完之后的切流顺序（预告，各步仍需你批准）

1. `ats cutover consumer health information` → 你批准 → `switch information`。
2. 生产里正常的组合级 Information 运行即走新路径（这一步调用模型，费用沿用你批准的额度），观察 N 个交易日。
3. 演练一次 `rollback information` 再 `switch information`（9.5）。
4. 同样方式切 Fundamental（含定时 PEAD 准备任务）。
5. 之后再进入调度切换（10.4）。
