# Tasks

任务编号沿用旧规划 `refactor-workflow-dataflow-architecture` 第 11 节：`F.0.x` 为 Phase F 前置接收，`11.x` 为实施段。新增任务以 `F.1.x` / `F.2.x` 标注。分组顺序即 design.md 的 Migration Plan 阶段顺序；每组自带其测试与文档，不把测试与文档延后到末组。

**全程约束**：本阶段不重建数据平台、不重复全量采集、不改动 A–E 已验收契约与门禁标准；真实 live route 切换保持锁定，只交付门禁、runbook 与演练；未取得资格的消费者保持稳定旧路由。

**实施侧记录在 [`docs/validation/PHASE_F_GROUP_PROGRESS.md`](../../../docs/validation/PHASE_F_GROUP_PROGRESS.md)**，不在本文件。本文件只记「做没做」，那份记录记「验证到什么程度、什么还没做完、为什么没做」——各组查出的自身缺陷、纠正过的误判、待处理项的 owner 与是否阻塞后续，以及统一 fix 的顺序。第9–13 组的验证/演练完成后再统一处置待处理项，不在实施中随手修（理由见该文件 §0）。

**强制 Guardian（`tests/test_phase_f_record_guardian.py`）**：**勾选≠ 完成**。每组任务全部勾选后，记录文档必须有一节 `### 第 N 组 · 任务 X.Y–A.B · <主题>`，且该节须写明三件事——

1. **验证/演练结果**（含「结论：」）
2. **后续注意/待修复项**（「本组无遗留待办」也是合法结论，但必须写出来，不能靠留白表达）
3. **为何现在不修**（不留理由的待办，下一轮要么被重新讨论一遍，要么被当成疏漏而擅自修掉）

守卫从**本文件的勾选状态推导**要求，不维护手写清单——手写清单本身是要同步的第二份状态，会在有人新增一组、勾了 checkbox 却忘登记时静默失效，那正是要防的失效模式。另见 `tests/test_phase_f_progress_doc.py`（校验记录与代码/配置一致）。

**顺序约束（design 决策 9/10，违反即导致资格自失效）**：

1. **进程级 broker write 禁令与隔离运行环境必须先于任何接入核验**（第 1 组 → 第 7 组依赖它）。
2. **取证必须整体后置到代码冻结之后**（第 2–5 组为代码冻结点，第 6 组起才取证）。第 2–5 组不得登记证据。
3. **切流实现 SHALL NOT 落在受指纹约束的路径集合内**（`src/ats/data/assurance.py`、`src/ats/data/consumer_api.py`、`config/data/structured.yaml`、`config/data/unstructured.yaml`、`config/data/target_dataflow_coverage.yaml`、trader/clerk 的 `authorization.py`/`decision/repository.py`/`clerk.py`、chief/risk 的 `state_api.py`/`config/risk.yaml`）。凡必须触及者（如授权加代次绑定），SHALL 安排在第 6 组取证之前完成。
