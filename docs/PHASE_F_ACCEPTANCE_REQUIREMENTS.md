## 已明确裁决的解释

- 本次选择 Event，就满足 Event；选择 Routine，就满足 Routine。未选模式不替代其他必需分析类别，也不额外强制运行两种模式。
- 单 Agent、依赖子流程和完整流程分别验收。完整流程全部必需分析必须成功；配置中存在的其他 Workflow 不自动成为单任务运行的前置条件。
- 旧结果不是新结果的正确性判据。旧专属算法故障经逐项证据确认可不阻塞；新契约、共享依赖、旧入口失权和真实下单安全仍必须通过。§15.5 的核心测试全绿不能用“旧流程问题”笼统豁免。
- Trader 采用方案 A。隔离环境可以通过 FakeBroker 测试完整批准/下单/Clerk 链；真实订单仍须独立满足交易审批与写入权限。
- 上线一次批准，在批准范围内持续运行直到主动停用。部署动作凭据、数据查询窗口、运行 as_of 和数据 TTL 分别处理；每次运行自动检查当前输入及停止状态，历史有限授权不自动升级。

## 测量纪律

按 §15.1 和 [测试基线条件](TEST_BASELINE.md)，最终测量使用 `./scripts/run_tests.sh`，由它执行 `uv sync --all-extras` 与 `uv run pytest`。定向测试用于验证对应改动；它们的通过数不能冒充全量基线或生产上线结论。

必需用途应在运行前从选定请求的依赖闭包和目标角色契约推导，不能从已成功执行的报告倒推。`verify_plan_coverage` 仅核验选定分析任务闭包；它不证明 Chief/Risk/Boss/Trader/Clerk 全链路或生产清零。配置展开清单中的重复 task-scope 数量只用于盘点，不能直接作为上线必须执行次数。

每个失败登记原始结果、原因、新路径可达性、受影响需求及修复或排除证据。候选运行、工程演练、当前资格、报告签核、实际生产观察和退役条件分别记录。受保护实现变更后必须重新冻结和补验，未完成事项保持待办。
