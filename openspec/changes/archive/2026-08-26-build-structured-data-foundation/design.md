## Context

见 proposal.md。当前仓库并非完全没有结构化底座：`measurement_series` / `measurement_points` 已能保存带修订的数值点，`DataProducts.metric_series()` 已支持 `as_of` 和 DataFrame，台湾财政部、韩国 ECOS 与 TrendForce 也已有确定性序列适配器。但这套能力尚处于验证阶段：主要财务和 Consensus 仍由 Workflow 运行时获取，原始来源快照没有统一保存，指标语义较薄，来源优先级和跨源对账尚未成为平台契约。

现有 `ats.sqlite` 同时承载 Workflow 状态、决策记忆和首期数据平台表。当前规模仍适合单机 SQLite，本阶段没有必要先引入 PostgreSQL、湖仓或分布式时序数据库；但新增能力必须通过独立 repository / data product 边界访问，避免将来物理拆库时再次修改所有 Agent。

阶段一的统一文档资产已经提供 document、version、span、来源和准入状态。阶段二需要复用这些身份和血缘，而不是把文档正文复制到结构化数据库。来源于文档的 ARR、融资金额等数值，其可信路径与 API 数值不同，也不能因“可转成 float”就绕过证据核验。

## Goals / Non-Goals

**Goals:**

- 在保持现有 Workflow 正常运行的前提下，将结构化数据变成独立于 Agent 的共享平台能力。
- 建立可扩展的接入骨架，使新增数据源主要增加适配、映射和质量规则，而不是新增一套存储与查询逻辑。
- 保留原始来源版本、标准化观测 vintage 和历史可见时点，支持真实的 `as_of` 重放。
- 让 SQL、Pandas、图表和 Agent 数据产品基于同一受治理视图。
- 通过分阶段、逐来源验收完成首批公司、地区和证据型行业数据迁移。

**Non-Goals:**

- 不在本变更中持久化任何粒度的 ticker 股价、OHLCV、订单簿、期权链、Greeks 或隐含波动率；这些数据继续由 IBKR/yfinance 等运行时来源按需查询。
- 不试图在首期建立覆盖所有行业的通用指标本体；只建立可演进的注册与别名机制。
- 不自动相信模型从文章中提取的数值，也不把所有新闻数字批量结构化。
- 不在本变更中用一个 Provider 覆盖所有地区、证券和指标；缺失与口径差异必须显式存在。
- 不立即删除旧取数函数或旧 measurement 表；退役以消费者切换和真实对账为前提。
- 不把 SQL 入口设计成可任意修改平台数据的管理数据库接口。
- 不承诺 structured snapshot 重放未持久化的股价和期权输入；需要保留的交易决策结果仍由既有决策记忆/Journal 负责，而不是把行情复制进本平台。

## Decisions

### 1. 以“可治理的观测”而不是“任何数字”定义结构化层

结构化层的最小业务对象不是一个 float，而是一项关于某个经济实体、某个指标、某个覆盖期间或事件的观测，并且知道来源何时发布、系统何时看到、采用什么单位和口径。

据此分成三条进入路径：

1. **来源原生结构化数据**：API、CSV、XBRL、Provider Parquet 等确定性记录，经映射和校验后发布。
2. **证据型结构化候选**：从公告、新闻或研报得到的融资、ARR、产能等数值，先关联文档证据并核验，再发布。
3. **派生计算**：同比、环比、滚动统计、跨源差异和换算值，由已发布观测按版本化公式计算，不伪装成来源原始值。

这一区分比按“公司数据/宏观数据/行业数据”分别建库更重要，因为它决定了准入强度和血缘。替代方案是只要能数值化就写入同一张表；该方案实现简单，但会把模型误读、来源估算和官方数值混成同等级事实，因此不采用。

### 2. 运行时市场数据是相邻能力，而不是持久数据集

ticker 股价与期权行情变化快、查询入口现成，长期复制会带来高频调度、授权、容量和时效责任，却不提升本阶段财务与行业研究事实的可信度。因此它们继续由现有 IBKR/yfinance 适配器按需查询，不注册为 structured dataset，也不产生 raw artifact、measurement series 或 vintage。

Workflow 编排层可以在同一次分析中组合两类输入：从 DataProducts 获取可重放的财务、Consensus、区域和行业事实，从运行时适配器获取当下股价或期权状态。两者在返回对象和文档中必须标明 `persistent` 与 `runtime`，避免使用者误以为 SQL/Pandas 能查询行情历史。structured snapshot manifest 只覆盖持久层输入；若某次决策需要审计当时成交价或市场状态，由既有决策记录保存该次使用结果，而不是建设行情副本。

替代方案是将日线作为低频例外存储，但这仍会引入复权、公司行动、交易日、跨市场时区和数据修订责任，并为未来期权持久化制造错误先例，因此不采用。

### 3. 采用五段式结构化生产线

```text
来源适配器
→ 原始快照与采集运行
→ 标准化候选与中央准入
→ 共享观测及 vintage
→ 查询、计算与数据产品
```

- 适配器只理解 Provider 协议和原字段，不直接决定 Agent 观点。
- 原始层先保留本次实际看到的内容或可复现切片。
- 中央准入统一执行实体、指标、期间、单位、内容完整性和重复检查。
- 观测层保存来源事实及修订，不保存同比/环比等可重算结果。
- 数据产品层负责来源选择、计算、横截面和上下文交付。

这样新增来源不会修改消费者，新增 Agent 也不会复制采集逻辑。与阶段一文档状态机一样，采集成功和准入成功是两个独立事件。

### 4. 首期逻辑分层，暂不强制物理拆库

首期继续以 SQLite 作为来源目录、采集账本、指标注册和标准化观测的权威事务存储，并以内容寻址文件保存较大的 JSON、CSV、XBRL 或 Provider 切片。现有 measurement 表通过加法迁移扩展或由新 repository 兼容读取，不对旧库做破坏性重建。

应用代码只通过结构化 repository 与 DataProducts 访问。默认可以与 `ats.sqlite` 同库部署，配置上允许使用独立 structured database 路径；待写入并发或规模成为真实瓶颈后，再把实现迁移到 PostgreSQL 或将大规模历史序列下沉 Parquet/DuckDB。

选择这一方案而不是立刻建设 DuckDB + Parquet 湖仓，是因为当前最大的风险是语义、时间与数据质量，而不是扫描性能。DuckDB 仍可在 defeatbeta 等远程 Parquet 适配器内部做 predicate pushdown，但它不是首期平台真相源。也不选择只存文件，因为版本准入、事务状态和历史时点查询需要可靠目录。

### 5. 数据模型围绕稳定身份而非 Provider 表结构组织

逻辑上保留以下对象，具体字段由实现阶段在现有表上渐进扩展：

- **Source / Dataset**：谁提供、覆盖什么、多久更新、是否可保存、何时需要回退。
- **Raw Artifact / Query Slice**：本次采集实际看到的来源版本。
- **Metric Definition**：指标含义、单位族、周期、累计/单季属性和允许转换。
- **Series Identity**：来源、实体、指标及必要维度共同确定的稳定序列。
- **Observation Vintage**：某个期间或事件的一次数值版本及其时间语义。
- **Derivation Definition**：派生公式及其版本、输入和窗口要求。
- **Evidence Link**：文档型数值对应的 document/version/span 与核验状态。
- **Data Snapshot Manifest**：一次 Agent 分析实际使用的观测与计算版本集合。


Provider 的未知字段不会被硬塞进错误指标，也不会丢弃：它们留在原始快照和待映射清单中。替代方案是为财务、宏观、Consensus 分别设计互不相干的事实表；虽然短期查询直观，但会复制来源、vintage、质量和血缘逻辑，因此只在数据产品层提供领域视图，不在治理层复制平台机制。

### 6. 使用四类时间表达真实可见性

平台区分：

- 数据实际覆盖的期间或事件时间；
- 来源对外发布或申报的时间；
- 系统首次获取并可用于分析的时间；
- 后续修订或再次获取的时间。

`as_of` 以“当时系统能够知道什么”为准：必须同时满足已经对外发布且已经被系统获取。若 Provider 不提供可靠发布时间，例如部分 Consensus 接口，只把抓取时间作为 `known_at`，绝不推测一个更早历史。相对标签如 yfinance 的 `0q` 必须在入库时绑定到具体公司财期，避免季度滚动后同一标签含义改变。

替代方案是只保留 period + fetched_at；这无法区分迟抓的旧数据与新发布的数据，也无法正确处理修订，因此不采用。

### 7. 来源优先级按数据集和用途配置，而不是全局固定

平台保留多个来源的独立观测，再生成可解释的首选视图：

- 美国公司财务报表以官方 SEC/XBRL 或公司披露为首选；defeatbeta `stock_statement` 用于便捷回填、非关键字段补充和交叉检查。
- defeatbeta 数据集由 HuggingFace 承载时，HuggingFace 只是传输/托管渠道；业务来源身份仍是 defeatbeta 对 Yahoo Finance 等上游的结构化镜像，血缘需同时记录托管快照和上游声明。
- 市场 Consensus 首期复用现有 yfinance 数据，按实际抓取快照沉淀；未来接入 FactSet 或其他授权源时并列保存，不覆盖旧来源。
- 台湾/韩国出口使用官方数据作为主源，先保存水平值，变化率由平台计算。

首选来源可因主源陈旧或不可达而回退，但结果必须说明实际来源和原因。绝不对冲突数值做无解释平均。

### 8. 指标注册采用“核心定义 + Provider 映射 + 待映射池”

指标注册表先覆盖首批研究必需指标，不追求一次穷尽。核心定义描述研究含义和可比性，Provider mapping 负责把 XBRL concept、statement 行名、官方统计字段或 Consensus 字段映射进来。

无法确认的 Provider 行项目进入待映射池并出现在覆盖报告中。只有语义相同的字段才复用同一指标；GAAP/non-GAAP、单季/累计、reported/consensus 等必须保留区分。人可以增加映射，新版本映射只重做标准化，不需要重新下载来源快照。

替代方案是直接采用某一 Provider 的字段名作为全局指标；这会把供应商锁定传递给所有 Agent，也无法跨来源对账，因此不采用。

### 9. 数据接入按三种代表性形状分批验证

首批不是按业务重要性把所有来源同时改完，而是用不同数据形状逐步验证平台：

1. **官方月度序列**：先迁移台湾/韩国出口，验证原始水平、发布时间、历史回填和派生变化率。
2. **复杂财务与预测数据**：迁移官方财务、defeatbeta `stock_statement` 和 Consensus，验证财期映射、多来源冲突、修订和相对预测期。
3. **证据型事件数据**：以少量 OpenAI/Anthropic 融资、估值或 ARR 样本验证 document lineage、人工核验和纠错，而不是立即大规模自动抽取。

每一批完成确定性 fixture、隔离库集成测试、真实源 smoke test、质量报告和旧路径对账后，才进入下一批；失败不阻塞已经通过的来源继续运行。

### 10. 派生计算采用查询时计算，必要时只物化可丢弃缓存

同比、环比、滚动统计、跨源差异等通过版本化 derivation registry 定义。默认从观测 vintage 计算，结果带公式版本和输入集合。图表或重复查询需要时可以物化缓存，但缓存不是权威事实，删除后可重建。

现有台湾/韩国适配器中提前生成的 yoy/mom 在迁移时改为：适配器返回来源水平，派生层统一计算；兼容输出在切换期仍可渲染相同结果。

替代方案是把所有派生值永久写入 measurement points；这会让公式升级、修订传播和历史重算变得含糊，因此不采用。

### 11. SQL 是只读分析面，DataProducts 是稳定产品面

Agent 继续优先使用 DataProducts：指标序列、横截面、公司快照、质量与血缘。Pandas 由相同查询结果构造 DataFrame。SQL 通过受治理的只读视图或只读连接开放，暴露的是 accepted 观测、指标目录、来源健康和血缘，而不是任意业务表，也不提供写权限。

这样既满足研究者临时分析，又不让 Agent 依赖物理表名。SQL 与 DataFrame 必须用同一来源选择、vintage 和质量规则做一致性测试。

### 12. 三类角色文档是产品接口的一部分

实施期新增三份独立文档，并由 `DATA_ARCHITECTURE.md` 作为总入口：

- `docs/STRUCTURED_DATA_DEVELOPER.md` 面向开发者，覆盖设计原则、组件职责、领域对象、组件架构图、采集/准入/查询数据流图、适配器契约、扩源示例和测试分层。
- `docs/STRUCTURED_DATA_OPERATIONS.md` 面向运维者，维护已接入、计划接入、未接入和 runtime/excluded 来源矩阵，以及认证、调度、保存政策、QPS/限流、请求预算、缓存、重试退避、故障排查、扩源步骤和验收门。
- `docs/STRUCTURED_DATA_USER_GUIDE.md` 面向使用者，提供指标发现、CLI、Python、SQL、Pandas、`as_of`、横截面、派生计算、分类、血缘及 Agent/Workflow 接入示例，并说明何时改用 IBKR/yfinance。

QPS 只记录 Provider 官方说明或实测可证实的限制；没有权威数字时标记 `unknown`，同时给出可配置的保守请求预算，不把内部默认值描述成外部事实。代码中的来源注册、运维矩阵与文档通过测试或生成式检查对账，避免实现已经改变而手册仍停留在旧状态。

替代方案是把所有内容继续堆在 `DATA_ARCHITECTURE.md`，但不同角色很难找到可执行信息，来源状态和示例也更容易失真，因此采用总览 + 三份角色手册。

### 13. 证据型数值使用“候选—核验—发布”工作台

融资和 ARR 等数据通常来自非结构化披露，设计上不要求 LLM 直接写 measurement。抽取器只产生候选和 evidence link，中央准入做确定性检查；首期由人工确认关键样本。核验记录保存责任人和时间，纠错通过新状态或新 vintage 完成，不删除旧证据。

一手公司披露、监管文件、可靠媒体转述和机构估算分别保留来源等级。多篇文章转述同一轮融资时先按事件去重，不把媒体数量误当作多次融资。后续若真实规模需要，可以在独立 OpenSpec 变更中增加半自动审核界面。

### 14. 质量门按数据集定义，平台统一呈现

不同数据形状不能套用同一完整性阈值：

- 财务数据检查财期连续性、statement 平衡关系、累计/单季口径和跨源差异；
- Consensus 检查目标财期解析、快照年龄和关键字段覆盖；
- 区域序列检查官方发布时间、月份连续性和单位变化；
- 证据型数值检查原文完整性、实体/指标/期间/单位与核验状态。

平台统一输出 coverage、accuracy/reconciliation、freshness、completeness 和 availability 五个维度，但阈值来自数据集配置。来源不可达、未发布和真无覆盖不会被合并成一个 missing。

### 15. 来源配置与可执行适配器使用受控运行注册表连接

`config/structured_data.yaml` 继续是来源、数据集、预算和质量规则的机器真相源，但 YAML 中的 adapter 名称不能动态 import 任意 Python 对象。平台维护一个受控运行注册表，把稳定 adapter key 映射到工厂和请求约束；新增来源必须同时完成配置登记、适配器实现和运行注册，统一校验命令会检查三者闭环。

统一 `ingest` 接口根据来源目录构造 `FetchRequest`，要求调用者显式提供来源需要的实体、期间或 query scope，并允许把数据库和 artifact 根目录指向隔离位置。它在执行前读取来源发布模式，拒绝 runtime/excluded，也不会用一个万能调度规则猜测所有 Provider 的参数。现有专项 smoke 脚本保留为深入诊断工具，但不再是新增来源上线的唯一入口。

替代方案是直接在 YAML 中配置模块路径并反射加载；它扩展方便，但扩大配置执行面、难以静态验证，也让适配器构造参数不透明，因此不采用。

### 16. 发布采用质量门驱动的可回滚运行覆盖层

`catalog_status` 表示能力成熟度，source/consumer mode 表示当前运行选择，两者不能混为一个字段。发布管理器先生成 release check：检查配置完整性、适配器可运行、最近采集状态、关联数据集质量维度和 runtime 边界；检查结果可被 CLI 和自动验收复用。

运行覆盖状态保存在可配置的本地 release overlay 中，默认位于 `var/structured_data/releases.yaml`。`source_mode()` 和 `read_mode()` 按“环境变量 → release overlay → checked-in config → legacy 默认”的顺序解析，从而无需为一次运行切换修改 Git 配置。`publish` 默认只做预检，只有 `--apply` 写入 overlay；`rollback` 也是显式、可审计和非破坏性的。发布来源只开放统一采集路径，不自动替所有消费者切换读取；消费者发布必须单独指定并通过其对账条件。

替代方案是让 CLI 直接改写 `config/structured_data.yaml`；这会把运行操作与代码审查混在一起，并使回滚依赖 Git，因此不采用。

### 17. 数据目录动态生成，Skill 只承载 Agent 决策规程

数据发现由静态目录和 repository 当前状态联合生成：静态层回答“注册了什么、语义和边界是什么”，运行层回答“现在实际有什么 accepted 数据、哪些实体/指标/期间可查、最后何时可见、质量是否通过”。`catalog`、`describe`、`availability` 和 `examples` 共用同一服务，CLI 与 DataProducts 返回相同结构；示例命令从真实覆盖选择数据集/指标/实体，空库时明确输出 no-data 而不是伪造例子。

仓库内提供 `structured-data-consumer` Skill，适用于会自主规划查询的 Agent。Skill 的稳定规则是先发现、再检查、后查询，并保留 `as_of`、质量和血缘；它不复制指标清单，而是指向动态命令和 DataProducts。PEAD、Sector、Chain 等确定性 Workflow 继续使用代码 API、兼容 DTO 和 feature flags，避免 Prompt 变化成为运行依赖。

替代方案是只写一本更长的使用手册；手册适合解释概念，却不能让 Agent 自动发现当前覆盖，也不能防止示例随数据库变化失真，因此采用“手册 + 可执行目录 + Skill”的组合。

## Risks / Trade-offs

- [结构化平台范围过大，实施周期失控] → 以三种数据形状为检查点，每一批独立验收和切换；后续新 Provider 另立小变更，不在本变更无限扩源。
- [SQLite 在并发写入下达到瓶颈] → 首期只覆盖低频研究数据，明确排除行情与期权；repository 隔离物理存储，记录真实规模和锁等待后再迁移。
- [财务指标映射比预期复杂] → 从核心指标和 covered universe 开始，未知行项目进入待映射池；不以“全部字段映射”作为首期上线门槛。
- [第三方镜像与官方数据冲突] → 两者并存、显式主源、自动差异报告；关键财务默认不以第三方最近抓取时间压过官方披露。
- [Consensus 缺乏可靠发布时间导致伪历史] → 从系统首次抓取日起建立真实快照，不回填无法证明的历史；覆盖报告显示历史起点。
- [原始快照占用磁盘] → 内容寻址去重、按来源保留策略管理；大数据集只保存命中切片与复现元数据，不盲目复制整个镜像。
- [文档型数值被误读为可信事实] → 默认隔离、证据链接、人工核验首批样本；模型置信度永远不能单独放行。
- [双写期间新旧结果不一致] → 消费者级 reconciliation gate；不一致时保持旧读路径并保留差异样本，而不是调宽容差掩盖问题。
- [首选来源规则隐藏数据差异] → 首选视图之外保留来源并列视图和 conflict 状态，数据产品可请求严格单源或全部来源。
- [角色文档随实现演进而失真] → 来源矩阵、示例命令和关键阈值纳入发布检查；文档变更是适配器接入和验收的完成条件。
- [发布命令误切换生产读取] → 默认只做预检，状态修改必须显式 `--apply`；来源与消费者独立发布，overlay 可立即回滚且不删除数据。
- [动态目录把注册能力误报为数据覆盖] → 分开输出 catalog status、release mode、accepted observation count 与 quality status；空库示例明确 no-data。
- [Agent Skill 与真实接口漂移] → Skill 不复制数据清单，契约测试验证其引用的 CLI/API，目录示例由实现动态生成。
- [Provider 没有公开 QPS] → 运维文档标记 unknown，采用可配置保守预算和退避，根据真实健康记录调整，不伪造外部约束。

## Migration Plan

1. 扩展现有结构化 repository 边界、来源目录、指标注册、原始快照、观测 vintage 和质量状态；以加法迁移保持旧库可读。
2. 为现有 `measurement_series` / `measurement_points` 建兼容读取与迁移审计，验证旧记录在新时间和指标语义下无静默改写。
3. 先迁移台湾/韩国出口：历史回填原始水平，统一计算 yoy/mom，与当前 Chain 输出对账后独立切换。
4. 为 ticker 股价与期权增加 runtime/excluded 边界测试，确认现有 IBKR/yfinance 路径保持工作且不会向结构化库写入行情。
5. 迁移公司财务与 defeatbeta `stock_statement`：建立核心指标映射、财期解析、官方/镜像并列与差异报告；先影子运行，不立即关闭旧 fundamentals。
6. 迁移 Consensus：把相对期间绑定到具体财期，从切换日起积累真实快照；与现有 PEAD 输入对账后再切换。
7. 以少量已知 OpenAI/Anthropic 融资、估值和 ARR 事实验证证据型候选、人工核验、事件去重和文档血缘。
8. 上线统一指标、横截面、SQL/Pandas、血缘和质量产品，为每次分析记录 structured snapshot manifest。
9. 交付并验证开发者、运维者和使用者三份角色文档，确保来源状态、QPS/预算、示例和验收门与实现一致。
10. 增加受控来源运行注册、隔离采集、release check、显式发布/回滚和 release overlay，并让来源模式实际约束统一采集入口。
11. 增加动态 `catalog`、`describe`、`availability`、`examples` 产品及 Agent Skill，随后以运维者、使用者和 Agent 三种路径走通验收。
12. 按消费者逐一切换并观察至少一个完整更新周期；只有在覆盖、对账和回滚演练通过后，才单独提出删除旧路径的变更。

回滚以来源或消费者 feature flag 恢复旧读取路径。新增表、原始快照和观测 vintage 不删除；它们保持只读审计价值。任何物理拆库都在本阶段稳定后另行设计，不与业务数据迁移同时进行。

## Open Questions

- 大型 Provider 原始切片的默认保留期限和磁盘预算，可在首次真实规模报告后确定，不影响内容寻址与血缘设计。
- 首批核心财务指标清单应由 PEAD、Sector 和图表实际查询共同收敛；未知行项目机制允许该清单渐进扩充。
- 未来付费 Consensus 或财务源的授权与优先级在真正接入时配置，不改变多来源并存和首选视图原则。
