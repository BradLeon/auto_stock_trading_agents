# Design

## Context

- **现有调度（美东时间）：**
  - chief-daily：周一至周五 09:45；
  - information-brief：08:00；
  - fundamental-routine、technical-review：08:30；
  - clerk-daily：18:00（台北 07:00）。
- **已有能力：** 定时运行的首席处于隔夜时段时，自动使用 overnight venue；手动运行仍走常规时段。
- **执行约束：**
  - 隔夜只接受限价单；
  - 执行前检查要求 30 秒内的实时买卖价、点差不超过 1%；
  - 审批必须在隔夜时段关闭前完成，否则执行前检查要求重新审批。
- **11-06 探测的点差：** 大盘股约 0.1%–0.4%（例如 NVDA 183.84/184.15）；部分标的没有最新成交价（AVGO 的 last 为 NaN），但有买卖价。

## Goals / Non-Goals

**Goals：**
- 研究、首席、审批、执行都在台北白天完成。
- 时段外不会发出隔夜订单。

**Non-Goals：**
- 不做“隔夜 + 日盘”的连续订单（`ib_async` 2.1.0 不支持 `includeOvernight`）。
- 不改风控规则本身。

## Decisions

### D1. 时间表（台北时间，冬令）

| 任务 | 现在 | 前移后 |
|---|---|---|
| clerk-daily | 07:00 | 不变 |
| information-brief | 21:00 | 08:30 |
| fundamental-routine、technical-review | 21:30 | 09:00 |
| chief-daily | 22:45 | 10:30 |
| 审批截止 | — | 收盘前 4 小时（冬令 12:50，夏令 11:50） |

**cron 一律用 Asia/Taipei 时区声明。** 美国夏令时期间，隔夜时段在台北提前一小时（约 08:00–15:50）。上表时间在冬夏令都落在时段内，所以不随夏令时调整。

### D2. 运行前的时段判定

chief-daily 触发时先判定隔夜时段是否开放，依据 OVERNIGHT 合约的交易时段与交易所日历：
- 未开放（周六、美国节假日、意外休市）：记 `skipped_session_closed`，不产生提案。
- 开放：继续运行，审批请求写入截止时间 = 收盘时间 − 4 小时与审批过期时间两者中较早者。

### D3. 未成交订单

隔夜时段收盘前 10 分钟，交易员撤销仍未成交的隔夜订单，记 `cancelled_session_end`。下一个首席周期按最新持仓重新评估，不把挂单带入常规时段。

**理由：** 隔夜限价是按隔夜报价定的，带入常规时段会以过期的价格依据成交。

### D4. 流动性保护

隔夜时段单笔订单金额上限取以下两者中较小者：
- 常规时段的上限；
- 该标的隔夜时段盘口买一或卖一数量 × 价格 × 5。

点差上限维持 1%。超过上限的订单拆成多笔、留在下一周期，或缩量。按现有风控的“缩量”路径处理，不新增规则。

### D5. 观察期

前移后先保留两周观察：每天记录隔夜点差、成交率、撤单数和审批耗时。观察结束由用户决定是否保留。

## Risks / Trade-offs

- [资讯截止提前，美股盘中新闻要到次日才进入研究] → 事件路径（财报日历触发）不受影响；日常路径接受约 12 小时的信息滞后，换取审批人可响应。
- [隔夜成交率低于预期] → D5 的观察数据会显示出来；回滚只需改回 cron。
- [小盘标的隔夜无报价] → 执行前检查 fail-closed，订单不提交，并在审批结果中写明原因。

## Migration Plan

1. 实现 D2、D3、D4。
2. 用 dry-run 在台北白天跑一次完整链路。
3. 改 cron，进入两周观察。
4. 用户决定保留或回滚。

回滚：恢复两个 YAML 中原来的 cron。
