# Design

## Context

- **现有调度（美东时间）：**
  - chief-daily：周一至周五 09:45；
  - information-brief：08:00；
  - fundamental-routine、technical-review：08:30；
  - clerk-daily：18:00（台北 07:00）。
- **已有能力：** 定时运行的首席处于隔夜时段时，自动使用 overnight venue；手动运行仍走常规时段。
- **执行约束：**
  - 隔夜只接受限价单；
  - 执行前检查要求 30 秒内的实时买卖价、点差不超过 1%；
  - 审批必须在隔夜时段关闭前完成，否则执行前检查要求重新审批。
- **11-06 探测的点差：** 大盘股约 0.1%–0.4%（例如 NVDA 183.84/184.15）；部分标的没有最新成交价（AVGO 的 last 为 NaN），但有买卖价。

## Goals / Non-Goals

**Goals：**
- 研究、首席、审批都落在审批人醒着的台北时间（2026-11-25 调整为台北晚上，见 D1）。
- 首席只在它所用时段开放时运行；时段外不会发出订单。

**Non-Goals：**
- 不做 IBKR 的“隔夜 + 当日”（OND）生效时间：它需要订单字段 `includeOvernight`，`ib_async` 2.1.0（PyPI 最新版，2026-11-25 核实）不支持。台北 21:00 的首席改用 D6 的延长时段 venue，效果相同（见 D6 理由）。等 ib_async 支持后再评估。
- 不改风控规则本身。

## Decisions

### D1. 时间表（台北时间，冬令）

| 任务 | 现在 | 前移后 |
|---|---|---|
| clerk-daily | 07:00 | 不变 |
| information-brief | 21:00 | 19:00 |
| fundamental-routine、technical-review | 21:30 | 20:00 |
| chief-daily | 22:45 | 21:00 |
| 审批截止 | — | 收盘前 4 小时（冬令 12:50，夏令 11:50） |

**cron 一律用 Asia/Taipei 时区声明。** 2026-11-25 调整：首席 21:00 台北 = 纽约 08:00（夏令 09:00），落在盘前，用 D6 的延长时段 venue。冬夏令都在盘前，不随夏令时调整。表中“审批截止”一行是隔夜 venue 的截止；首席 21:00 用延长时段，截止见 D6（冬令 01:00、夏令 00:00 台北）。

### D2. 运行前的时段判定

chief-daily 触发时先判定它将使用的时段是否开放：常规时段（交易所日历）、隔夜时段（交易所日历 + OVERNIGHT 合约的交易时段）、盘前延长时段（交易所日历，D6），依次取第一个开放的。
- 都未开放（周六、美国节假日、意外休市、盘后至隔夜之间）：记 `skipped_session_closed`，不产生提案。
- 开放：继续运行。隔夜与延长时段的审批请求写入截止时间 = 该 venue 的计时收盘 − 4 小时（系统里没有独立的“审批过期时间”，故只取这一项）。常规时段不设截止。

### D3. 未成交订单

隔夜时段收盘前 10 分钟，交易员撤销仍未成交的隔夜订单，记 `cancelled_session_end`。下一个首席周期按最新持仓重新评估，不把挂单带入常规时段。

**理由：** 隔夜限价是按隔夜报价定的，带入常规时段会以过期的价格依据成交。

### D4. 流动性保护

隔夜时段单笔订单金额上限取以下两者中较小者：
- 常规时段的上限；
- 该标的隔夜时段盘口买一或卖一数量 × 价格 × 5。

点差上限维持 1%。超过上限的订单拆成多笔、留在下一周期，或缩量。按现有风控的“缩量”路径处理，不新增规则。

D4 同样适用于 D6 的延长时段 venue（盘前盘口薄）。

### D6. 延长时段 venue（2026-11-25 新增）

首席在盘前（纽约交易日 04:00 至开盘）运行时使用 `extended` venue：
- 交易所 SMART，`outsideRth=True`，只收限价单，生效时间 DAY：订单在盘前、常规、盘后挂到 20:00 纽约（台北次日 09:00），由 IBKR 自动失效，不另设撤单。
- 报价：SMART 实时买卖价，≤30 秒，点差 ≤1%；当时处于盘前则 `session=extended`，已开盘则 `session=regular`。执行前检查读当时开放的那一段，所以开盘后批准的延长时段订单也能检查。点差超限的标的本轮跳过，其余照下（同隔夜）。
- 审批截止 = 当日常规收盘 − 4 小时（12:00 纽约，冬令台北 01:00、夏令 00:00），给成交留 4 小时常规时段。
- 只用于盘前：盘后（16:00–20:00 纽约）开始的提案离 20:00 失效不到 4 小时，不作为可运行时段。

**理由：** 台北 21:00 提交时，隔夜时段已于 16:50 台北收盘、下一段 09:00 台北才开，而 DAY 订单 09:00 台北已失效，所以 OND 与“SMART + outsideRth + DAY”在这个时间提交的效果相同。按盘前报价定的限价会带入常规时段（不同于 D3 对隔夜订单的处理），用户 2026-11-25 确认接受。

### D5. 观察期

前移后先保留两周观察：每天记录隔夜点差、成交率、撤单数和审批耗时。观察结束由用户决定是否保留。

## Risks / Trade-offs

- [资讯截止提前，美股盘中新闻要到次日才进入研究] → 事件路径（财报日历触发）不受影响；日常路径接受约 12 小时的信息滞后，换取审批人可响应。
- [隔夜成交率低于预期] → D5 的观察数据会显示出来；回滚只需改回 cron。
- [小盘标的隔夜无报价] → 执行前检查 fail-closed，订单不提交，并在审批结果中写明原因。

- [盘前点差宽、报价稀] → 点差 >1% 的标的本轮跳过；D4 的盘口上限缩量。
- [盘前限价带入常规时段，开盘跳空后可能以不利于新信息的价格成交] → 用户接受；限价本身封顶价格，D5 观察成交情况。

## Migration Plan

1. 实现 D2、D3、D4；D6（延长时段）。
2. 用 dry-run 跑一次完整链路（隔夜：台北白天；延长时段：台北 21:00 左右）。
3. 改 cron，进入两周观察。
4. 用户决定保留或回滚。

回滚：恢复两个 YAML 中原来的 cron。
